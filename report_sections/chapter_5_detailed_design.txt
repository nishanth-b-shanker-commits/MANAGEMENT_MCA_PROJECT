## 5.1. Introduction
This chapter explains the detailed design of our system components. It outlines the directories of the codebase and deep-dives into several core processing modules, detailing inputs, outputs, processes, and implementing code blocks.

## 5.2. Structure of the software package
The application is structured into decoupled frontend and backend directories, facilitating independent development and easy deployment.

## 5.3. Modular decomposition of the System

### 5.3.1. Module 1: Authentication and Session Security
This module handles secure account logins, role-based checks, and Two-Factor Authentication (TOTP). It also implements a client-side session timeout that automatically signs out the user after 160 seconds of inactivity.

#### 5.3.1.1. Inputs
- Username (String, matching registration handle)
- Password (String, plain-text security code)
- 2FA TOTP Code (6-digit dynamic number)

#### 5.3.1.2. Procedural details
1. The user enters their credentials. The server queries the database for the username.
2. It compares the password with the saved Bcrypt hash.
3. If 2FA is active, the system requests the 6-digit TOTP key and verifies it against the generated time-based secret.
4. On success, it issues a signed JWT token containing the user's role.
5. In the frontend, the React session monitors mouse, keyboard, and scroll movements, automatically logging out the user if no events occur for 160 seconds.

#### 5.3.1.3. File I/O interface
- Reads: Queries the Users collection for user details and security keys.
- Writes: Appends login events to the Audit Trails collection.

#### 5.3.1.4. Outputs
- Success: JWT session token, Username, and User Role.
- Failure: HTTP 401 (Invalid Credentials) or HTTP 403 (Pending Admin Approval).

#### 5.3.1.5. Session Inactivity Timeout Logic
The client-side inactivity monitor functions according to the following algorithm sequence:
- STEP 1: Verify the presence of an active user session context in the frontend. If no user is logged in, exit the routine.
- STEP 2: Initialize a local reference variables pointer for the inactivity timer handler.
- STEP 3: Define a reset callback function that clears any active timeout pointer and schedules a new timeout callback to trigger at exactly 160,000 milliseconds (160 seconds).
- STEP 4: Bind event listeners to the global window viewport object for mouse movement, key down, page scrolling, and click inputs, linking each event to the reset callback.
- STEP 5: If the scheduled timeout fires without reset, display a warning modal alert to the user, execute the logout cleanup routine, clear local cache keys, and redirect the user back to the login card view.
- STEP 6: On component unmount, clear active timer intervals and unbind all viewport event listeners to prevent browser memory leaks.

### 5.3.2. Module 2: Vessel Registry
This module allows shipping agents to register new merchant vessels. It verifies that the vessel is unique using the 7-digit IMO number.

#### 5.3.2.1. Inputs
- Vessel Name, Type, and Flag Country
- Owner details
- Gross Registered Tonnage (GRT) and Net Registered Tonnage (NRT)
- IMO Number (7-digit unique key)

#### 5.3.2.2. Procedural details
1. The agent fills out the registration form.
2. The system runs client-side validations to ensure the IMO is a 7-digit number.
3. The server checks the Vessels collection to reject duplicate IMO numbers.
4. If unique, the database saves the vessel record and links it to the agent's account.

#### 5.3.2.3. File I/O interface
- Reads: Queries the Vessels collection for duplicate IMO checks.
- Writes: Appends the vessel record to the Vessels collection.

#### 5.3.2.4. Outputs
- Success: HTTP 201 (Vessel registered successfully).
- Failure: HTTP 400 (Vessel with this IMO already registered).

### 5.3.3. Module 3: Voyage Clearance Stepper
This module manages the sequential approval workflow (Health -> Customs -> Traffic). It ensures that a voyage moves through each review stage in order.

#### 5.3.3.1. Inputs
- Arrival/Departure logs
- Cargo type, Crew count, Passenger count
- Lighthouse dues receipt details
- Port officer approvals and comments

#### 5.3.3.2. Procedural details
1. The agent files a voyage request. The stepper initializes its status to "PHO Pending".
2. The Port Health Officer submits their approval, moving the status to "Customs Pending".
3. The Customs Officer reviews cargo details and dues, moving the status to "Traffic Pending".
4. The Traffic Controller reviews berthing slots and grants final approval, changing the voyage status to "Cleared".
5. If any officer rejects the request, the stepper transitions the voyage status directly to "Rejected".

#### 5.3.3.3. File I/O interface
- Reads: Queries the Journeys collection to display pending clearances.
- Writes: Updates approval states and logs clearance comments.

#### 5.3.3.4. Outputs
- Success: Voyage status changed to "Cleared", enabling certificate downloads.
- Failure: Stepper halts or status transitions to "Rejected".

### 5.3.4. Module 4: Bilingual jsPDF Generation
Upon final clearance, this module renders bilingual PDF certificates on the client side. The certificates include seals, signatures, and a verification QR code.

#### 5.3.4.1. Inputs
- Cleared voyage details
- Department approval metadata
- Local host URL to generate the verification QR code

#### 5.3.4.2. Procedural details
1. The agent clicks "Download Certificate".
2. The jsPDF library runs, creating a PDF document with borders, headers, and emblem icons.
3. It draws bilingual labels in Hindi and English.
4. It compiles a QR code using the validation URL `verify-certificate/:journeyId`.
5. The PDF is compiled and downloaded directly in the agent's browser.

#### 5.3.4.3. Outputs
- Success: Bilingual PDF files (Certificate of Health Clearance / Port Clearance Certificate).
- Failure: Alert showing "Failed to compile document".

#### 5.3.4.4. jsPDF Layout Compilation Logic
The document drawing engine uses the following structured sequence:
- STEP 1: Instantiate a portrait orientation PDF document object with standard A4 measurements (210mm x 297mm).
- STEP 2: Configure green and gold tricolor borders. Render an outer rectangle at 5mm padding and an inner accent frame at 7mm padding using a line thickness of 1mm.
- STEP 3: Place federal headers in a bold Sans-serif font at 14pt. Center-align the bilingual title string "भारत सरकार | GOVERNMENT OF INDIA" at vertical position 20mm.
- STEP 4: Add sub-header ministry text at 11pt, centering "पत्तन, पोत परिवहन और जलमार्ग मंत्रालय" and "MINISTRY OF PORTS, SHIPPING AND WATERWAYS".
- STEP 5: Render the certificate category titles in bold at 16pt, displaying bilingual names for Health and Port Clearances.
- STEP 6: Write voyage parameters (Vessel Name, unique IMO registry number, Port Health declaration numbers, and dates) in regular 10pt text using 8mm line increments.
- STEP 7: Generate a Base64 encoded QR code string referencing the unauthenticated verification route. Draw the QR code image at coordinate offset (150mm, 220mm) with dimensions 40mm x 40mm.
- STEP 8: Save the output document locally under a structured filename containing the vessel's name.

### 5.3.5. Module 5: Offline LocalStorage Sync Adapter
To support offline operations, this module intercepts Axios requests and redirects them to a LocalStorage database copy when the backend is unreachable.

#### 5.3.5.1. Inputs
- Axios HTTP request instances (GET, POST, PUT, DELETE)
- Network connectivity status

#### 5.3.5.2. Procedural details
1. The Axios interceptor checks network availability and API responsiveness.
2. If the API is unreachable, the interceptor redirects requests to `mockBackend.js`.
3. The mock backend performs CRUD actions on the LocalStorage JSON records.
4. When the connection is restored, the adapter syncs the local records back to the MongoDB Atlas database.

#### 5.3.5.3. Offline Interceptor Setup Logic
The dynamic network redirection system operates according to the following algorithm:
- STEP 1: Instantiate a custom Axios API connection wrapper configured with default base URLs.
- STEP 2: Bind a request interceptor that retrieves the active authentication session token from local memory and injects it as an authorization bearer header.
- STEP 3: Evaluate network parameters: check window navigation flags and execute active pings to check server route availability.
- STEP 4: If mock flags are enabled or if the server connection fails, register local interceptor methods for POST, PUT, and DELETE queries.
- STEP 5: Redirect API queries to mock controller callbacks that execute CRUD logic on local JSON tables stored inside LocalStorage.
- STEP 6: When network ping checks succeed again, query cached items, make batch updates to MongoDB Atlas, and clear local tables.

### 5.3.6. Module 6: Sagar Setu AI Assistant Chatbot
This module integrates an on-screen conversational helper running client-side keyword matching. It maps user queries to specific help guides (Vessel registry instructions, 2FA configurations, or helpline support desks) in Hindi or English depending on active translation.

#### 5.3.6.1. Inputs
- Chat text input (String, query from user console)
- Active Language selection (English/Hindi)

#### 5.3.6.2. Procedural details
1. The user types a query in the chat box or clicks one of the quick options.
2. The chatbot parses keywords using regex check patterns.
3. It indexes translation mappings based on the language context.
4. It pushes user and bot messages to the conversation array, rendering them in standard speech bubble styles.

#### 5.3.6.3. Sagar Setu Bot Keyword Matching Logic
The conversational assistant processes user queries as follows:
- STEP 1: Capture the text input string entered in the chatbot input box.
- STEP 2: Check language settings. If set to English, load English response templates; if set to Hindi, load Hindi response templates.
- STEP 3: Normalize the text string: strip punctuation, convert characters to lowercase, and split into word tokens.
- STEP 4: Compare tokens against a regex keyword dictionary:
  - If keyword "vessel" or "register" is found: map response explaining the Vessel Registry tab requirements (IMO, GRT, NRT).
  - If keyword "dues" or "customs" is found: map instructions on paying Indian Light House dues.
  - If keyword "stepper" or "workflow" is found: describe sequential clearance stages (PHO -> Customs -> Traffic).
  - If no keyword match: return a generic support contact response.
- STEP 5: Append user message to active history array; trigger a 600ms delayed assistant reply bubble to simulate active processing.

### 5.3.7. Module 7: Government SMS Gateway Alerts
This module implements real-time visual alerts simulating notifications from a government cellular gateway. It informs shipping agents on their dashboard when officers approve or reject their requests.

#### 5.3.7.1. Inputs
- Clearance state changes (PHO approve, Customs approve, Traffic approve)
- Voyage details and agent contacts

#### 5.3.7.2. Procedural details
1. Officers execute reviews on their consoles. The backend database status updates.
2. The dashboard intercepts status change events.
3. The dashboard triggers a custom EventListener showing a floating SMS bubble with government formatting and timestamp logs.

### 5.3.8. Module 8: Main express server configuration
This module sets up the Express.js application, configuration parameters, and routes. It loads configuration keys, sets up CORS headers, initializes JSON parsers, and establishes connections to the MongoDB database cluster. It mounts REST route paths for authentication, user management, vessel registries, voyage clearances, and audit logs. It also serves compiled React static assets during production setups.

#### 5.3.8.1. Inputs
- Environment configurations (Port, DB URI strings, encryption salt keys).

#### 5.3.8.2. Procedural details
1. Reads environment parameters on bootup.
2. Initialises server middleware (CORS, body parser, static file routers).
3. Establishes DB client socket link to MongoDB cluster.
4. Mounts REST endpoints under defined path contexts.
5. Listens for incoming HTTP requests on the designated server port.

#### 5.3.8.3. File I/O interface
- Reads: Environment configurations `.env` files.
- Writes: Active logs to node terminal processes.

#### 5.3.8.4. Outputs
- Success: Console log indicating database connection and server listening states.
- Failure: Server crash log displaying exception details.

### 5.3.9. Module 9: Database pre-population seeding
This module seeds approved roles in the database. It connects to the MongoDB cloud database, hashes seed account passwords using Bcrypt, deletes existing legacy accounts to prevent conflicts, and inserts approved accounts for System Administrators, Ship Agents, and Department Officers.

#### 5.3.9.1. Inputs
- Static JSON documents mapping default roles and accounts configuration.

#### 5.3.9.2. Procedural details
1. Establish database connection socket.
2. Clear pre-existing documents from the Users collection to prevent collision errors.
3. Hash default user account passwords using bcrypt algorithm loops.
4. Write seed accounts to the collection in an approved state.

#### 5.3.9.3. File I/O interface
- Writes: Writes document arrays to Users collection in MongoDB database.

#### 5.3.9.4. Outputs
- Success: Console log indicating successful database pre-population seeding.

### 5.3.10. Module 10: Frontend API Axios service
This module sets up the React client communication gateway. It creates Axios instances with environment-specific base URLs and request interceptors to inject authorization headers automatically. It routes calls to the local mock database wrapper during offline operations.

#### 5.3.10.1. Inputs
- React app HTTP request descriptors.

#### 5.3.10.2. Procedural details
1. Instantiate Axios client configurations.
2. Inject bearer authentication header retrieved from localStorage key.
3. Intercept response payloads to trigger logouts if HTTP 401 or 403 occurs.

#### 5.3.10.3. Outputs
- Success: Formatted Axios wrapper instance for API calls.

### 5.3.11. Module 11: Vessel registration React layout
This module defines the UI components for registering merchant vessels. It implements React state bindings for form fields, client-side validations, submission handlers that dispatch HTTP POST requests, and warning triggers for duplicate entries.

#### 5.3.11.1. Inputs
- Form fields: Vessel Name, flag state, GRT, NRT, IMO number.

#### 5.3.11.2. Procedural details
1. Render input elements with state bindings.
2. Capture text input; validate IMO numeric pattern lengths.
3. Verify tonnage values are greater than zero.
4. Dispatch Axios POST requests to vessels backend router.
5. Capture response; trigger toast alerts.

#### 5.3.11.3. Outputs
- Success: Renders success toast alert; clears form fields.
- Failure: Renders error popup with validation error details.

### 5.3.12. Module 12: Authentication API routes controller
This module implements Express route controllers for authentication. It validates registration payloads, checks for duplicate usernames, runs Bcrypt encryption algorithms, and registers new accounts in a pending state. It checks password hashes, verifies Time-Based One-Time Passwords (TOTP), and generates JWT session tokens.

#### 5.3.12.1. Inputs
- Registration and Login request payloads.

#### 5.3.12.2. Procedural details
1. Receive request. Check for existing username document.
2. Run bcrypt password checks.
3. Verify TOTP 6-digit code against time-based algorithm calculations if 2FA is active.
4. Generate signed JWT token including user details.

#### 5.3.12.3. File I/O interface
- Reads/Writes: Users collection.

#### 5.3.12.4. Outputs
- Success: Signed JWT token string and role metadata.
- Failure: HTTP 400 or 401 status code with error details.

### 5.3.13. Module 13: Vessel registry API routes controller
This module handles CRUD actions on the Vessel collection. It processes POST requests to save new ships, checks IMO number uniqueness against existing records, retrieves vessels registered by shipping agents, and deletes invalid vessel documents.

#### 5.3.13.1. Inputs
- Vessel creation payloads.

#### 5.3.13.2. Procedural details
1. Receive request details. Extract IMO number.
2. Query Vessels collection for existing IMO matches.
3. If unique, save the vessel document and return success status.

#### 5.3.13.3. File I/O interface
- Reads/Writes: Vessels collection.

#### 5.3.13.4. Outputs
- Success: HTTP 201 Created status containing the new vessel document.
- Failure: HTTP 400 Bad Request status code.

### 5.3.14. Module 14: Voyage clearance API routes controller
This module manages the stepper state machine. It handles new voyage submissions, filters pending arrivals by department roles, and records approval decisions. It enforces sequential transitions (Health -> Customs -> Traffic), logs comments, and locks records after final clearances.

#### 5.3.14.1. Inputs
- Voyage entry logs, approval state updates, officer comments.

#### 5.3.14.2. Procedural details
1. Save voyage details in MongoDB. Set status to "PHO Pending".
2. Match approvals sequentially (Health -> Customs -> Traffic).
3. Set status to "Cleared" and generate certificate links when all three approve.
4. Set status to "Rejected" and lock the record if any officer rejects.
5. In procedural flows, validation controllers intercept duplicate arrivals and check dates limits.

#### 5.3.14.3. File I/O interface
- Reads/Writes: Journeys collection.

#### 5.3.14.4. Outputs
- Success: Updated voyage JSON document status details.

### 5.3.15. Module 15: Offline LocalStorage mock database manager
This module implements client-side LocalStorage CRUD logic. It emulates MongoDB collections in browser memory, intercepting API requests during connection outages. It processes user registrations, saves vessels, logs voyages, and manages offline stepper actions.

#### 5.3.15.1. Inputs
- Axios requests intercepted during server drops.

#### 5.3.15.2. Procedural details
1. Intercept request. Route to mock backend controller method.
2. Read JSON data from localStorage key.
3. Apply CRUD updates and save the JSON back to localStorage.
4. Sync local updates back to MongoDB when ping check succeeds.
5. To execute syncing, background routines run async calls that resolve network conflicts.

#### 5.3.15.3. Outputs
- Success: Mock JSON database records returned directly to React layout.
