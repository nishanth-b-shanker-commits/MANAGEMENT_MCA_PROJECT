## 4.1. Introduction
We selected MongoDB Atlas, a fully managed NoSQL cloud database service, to store the portal's persistent data. Relational databases enforce rigid schemas, which can cause scalability bottlenecks. In contrast, MongoDB's document-oriented NoSQL model allows storing voyage entries, clearances, and logs as flexible, JSON-like documents. The integration utilizes Mongoose ODM (Object Document Mapper) in Node.js, providing schema validation, type casting, and query helpers.

## 4.2. Purpose and scope
The database design ensures document integrity, data history, and audit compliance:
- Document Embedding: Voyage documents copy the vessel's details at the time of filing. This keeps the voyage's historical vessel data intact even if the primary vessel registry is modified.
- Collections Partitioning: Data is divided into collections for Users, Vessels, Journeys, and AuditTrails.
- Database Indexing: The system indexes unique keys like `username` in Users, `imoNumber` in Vessels, and `userId` across collections to keep query times under 500ms.

## 4.3. Table Definitions
The tables are mapped to MongoDB collections using Mongoose models:

### 4.3.1. User Collection
Stores login details, administrative statuses, and 2FA credentials.
It features a NoSQL document schema containing fields for the user identity and state. It maps a unique username string, Bcrypt hashed password representation, email address, role classification selector, onboarding approval status flag, Base32 security secret, and 2FA activation status.

### 4.3.2. Vessel Collection
Maintains ship records registered by agents.
It includes document properties for merchant vessels. It validates the unique 7-digit IMO numeric string registration identifier, records vessel classification types, logs registered flag states, details corporate owner descriptors, and saves gross/net tonnages in metric measurement values.

### 4.3.3. Voyage (Journey) Collection
Tracks voyage clearances and department comments.
It maps detailed voyage documents containing embedded snapshots of vessel specifications. It tracks voyage parameters like estimated arrival/departure logs, cargo classifications, captain credentials, lighthouse payment dues receipts, crew lists, and multi-department approvals and comments.

### 4.3.4. Audit Trail Collection
Maintains security logs of system transactions.
It records security logs chronologically. It maps the precise action execution timestamps, details user logins or profile modifications, and appends read-only summaries of actions performed.

## 4.4. ER Diagram
The Entity-Relationship (ER) Diagram shows the logical relationships between collections. A User Account (Agent) can own multiple Vessel Registry entries. The Voyage collection embeds the Vessel details as a static sub-document, preventing subsequent updates to the Vessel Registry from changing past voyage records. Each Voyage tracks clearances linked to the PHO, Customs, and Traffic officers. The Audit Trails collection records activities referencing the Username.

## 4.5. MongoDB Atlas Sharding and Replication Strategy
To maintain continuous operations at NMPA Mangaluru, the database utilizes a MongoDB Atlas replica set topology:
- Primary Node: Processes all write commands and logs them to the oplog collection.
- Secondary Nodes: Mirror the primary node in real time. If the primary node goes offline, the cluster holds an election to elevate a secondary node automatically.
- Horizontal Sharding: For scaling, collections are partitioned across server fragments using shard keys like `userId` and `imoNumber`. This balances database loads and keeps queries under 500ms.

## 4.6. Database Migration and Seeding Protocols
Deploying the database cluster requires pre-population seeding protocols:
- 1. Verification: The migration scripts check database connection states before starting commands.
- 2. Rollback: If connection errors occur, the script halts and rolls back active collections states to avoid data corruption.
- 3. Password Hashing: Seed accounts are created with secure password hashes compiled through local bcrypt libraries.
- 4. State Initialisation: Default roles (Admin, Agent, Health, Customs, Traffic) are loaded into the Users collection in an approved state.
This provides a ready-to-use, secure testing environment for port operators.

## 4.7. Database Backup, Archive and Disaster Recovery Protocols
To prevent data loss, the database implements backup schedules:
- 1. Automated Backups: The cluster triggers database snapshot captures every 6 hours, storing files across separate cloud zones.
- 2. Retention Windows: Daily database snapshots are retained for 30 days, while monthly archives are preserved for 1 year to satisfy audit checks.
- 3. Restoration Drills: Administrators execute mock recovery drills quarterly, verifying data consistency on test database setups.
This recovery plan ensures maximum database uptime and prevents operational disruptions.

## 4.8. Security Audits and Compliance Standards
To support national security standards, the database schema implements logging constraints:
- 1. Read-Only Audits: The Audit Trails collection prevents updates or deletions through application routes, keeping log lines unaltered.
- 2. Schema Restrictions: Mongoose validation layers check user roles before allowing writes, blocking access to unauthorized users.
- 3. Verification Hashes: Log events are combined with verification hashes to detect database tampering.
These measures ensure compliance with standard Indian information security protocols.
